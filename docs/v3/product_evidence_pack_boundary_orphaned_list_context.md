# 지시서 — 청크 경계에 고아가 된 numbered list의 context 보강

작성: 2026-08-03 · 대상: Codex · 상태: 실제 사례로 재현 확인, 수정 요청
대상 파일: `src/v3/product_evidence_pack.py` (`_short_numbered_list_units`)

---

## 0. 배경

Product Free RAG v1의 "목록 바로 앞 문장을 context로 연결" 기능과 "BGE 최고점 0.05
이내 complete_list 우선 예약" 규칙을 검증하다가, **청크 경계가 원인/원칙 문장과
번호 목록 사이를 정확히 갈라놓는 경우** 두 안전장치가 전부 무력화되는 실제 사례를
찾았습니다.

---

## 1. 재현된 실제 사례

문서: `던전앤파이터 운영정책 (2023-04-06 시행)`
(`document_sha256_2cd703888a9f68cdf48d4c898f40f1c4f427e81d4945d990c68ae10e0e654cc0`)

원문(문서 기준 3006~3259번째 글자 부근)은 원래 한 덩어리입니다.

```
[3-3] 회사는 고객의 정상적인 활동이나 고객 간의 사적인 분쟁에 개입하지 않는 것을
원칙으로 합니다. 단, 아래와 같은 경우에는 해당 행위를 경고하거나 게임이용을
제한할 수 있습니다.
① 비인가 프로그램 사용, 타인의 게임이용방해 등 원활한 게임 진행에 부정적 영향을
   준다고 판단될 경우
② 사적인 분쟁이라고 하더라도 불특정 다수의 고객에게 피해를 입히는 경우
③ 고객 간의 분쟁으로 게임 질서를 어지럽히거나 실정법을 위반하는 행동이라고
   판단될 경우
```

그런데 실제 청킹 결과:

```
chunk A: chunk_sha256_e7c9bce5a819e7c53d5034446b201e39f9b254396e12d0ded1746b4b01becaa0
  end_offset = 3259, overlap_chars = 200
  → "[3-3] 회사는... 원칙으로 합니다. 단, 아래와 같은 경우엔..." 이 청크 안에서 끝남

chunk B: chunk_sha256_92a99dd682cd5875dc7dced26f83b32b282a06dea3ae0c7a8373002fa67b5359
  start_offset = 3111, overlap_chars = 200
  → 실제 display_text가 "① 비인가 프로그램..."으로 바로 시작 (앞에 아무 것도 없음)
```

문서 원문에서 `"① 비인가 프로그램"`의 정확한 offset을 확인하니 **3111 — chunk B의
start_offset과 정확히 일치**합니다. `overlap_chars=200`이 설정돼 있는데도, 청크
시작점을 "깨끗한 줄바꿈"에 맞추는 로직이 하필 원칙 문장과 목록 사이의 그 줄바꿈에서
정확히 잘라버려서, **오버랩이 실질적으로 0으로 소진**됐습니다.

`_short_numbered_list_units`는 목록 unit의 `context_text`를 만들 때 **현재 청크의
display_text 안에서만** 앞 줄을 찾습니다(라인 354~368 부근, `preceding_lines`).
chunk B 안에는 목록 앞에 아무 줄도 없으므로 `context_text`가 `heading_path`만 남은
`'운영정책'`이 됩니다.

## 2. 실측 결과 — 안전장치가 이 경우 전부 무력화됨

`BAAI/bge-reranker-v2-m3`(실제 모델, mock 아님)로 세 가지 자연스러운 패러프레이즈를
`_atomic_reranker_text`로 감싸서 직접 채점:

| 질문 | 원칙문장 점수 | 고아가 된 목록 점수 | 격차 |
|---|---:|---:|---:|
| "...예외 조건이 뭐야?" | 0.9904 | 0.8161 | 0.1742 |
| "...개입하는 조건은 어떤 게 있어?" | 0.6751 | 0.0171 | 0.6580 |
| "...개입할 수 있는 경우의 종류를 알려줘?" | 0.6598 | 0.0356 | 0.6242 |

세 경우 다 "0.05 이내" 안전장치 범위를 훨씬 벗어납니다(0.17~0.66). 이 목록이 top
후보에서 밀리면, 답변이 "예외가 있다"고만 하고 실제 ①②③ 조건은 빠질 위험이
있습니다.

**비교 대조**: 같은 방식으로 "길드장 권한 위임" 목록(원인 문장이 같은 청크 안에
있었던 경우)에 실제 context를 붙이면 점수가 0.97로 올라 원인 문장(0.93)을 압도적으로
이깁니다 — **문제는 "context 보강" 메커니즘 자체가 아니라, 청크 경계가 그 보강 재료를
아예 빼앗아 갔다는 것**입니다.

---

## 3. 문제의 범위

전체 코퍼스에 대해 `_short_numbered_list_units`를 직접 돌려 확인한 결과:

```
전체 numbered-list unit: 647개
context_text가 heading_path뿐이거나 15자 미만인("고아") unit: 158개
```

이 158개 전부가 위와 같은 "청크 경계 스냅" 사례인지, 아니면 애초에 문서/섹션 맨
앞이라 원래 선행 문장이 없는(정상적으로 context가 빈약한) 경우인지는 구분이 안 된
상태입니다. 수정 전에 이 구분부터 필요합니다.

---

## 4. 수정 방향

**청킹·오버랩 설정 자체는 건드리지 마세요.** 원본 코퍼스도 불변으로 유지합니다.
수정은 `_short_numbered_list_units`의 context 구성 로직에만 국한합니다.

1. 목록 unit이 **자기 청크 안에서 선행 non-list 줄을 하나도 못 찾은 경우에만**
   (`preceding_lines`가 비어있는 경우), 같은 `parent_document_id`를 가진 **직전
   청크**(같은 문서 안에서 `chunk_index - 1` 또는 `start_offset` 기준 바로 앞)의
   **마지막 non-list 줄**을 가져와 context로 붙입니다.
2. 딱 한 청크만 거슬러 올라갑니다(두 청크 이상 거슬러 올라가면 무관한 내용을 끌어올
   위험이 커집니다). 그 한 청크에도 없으면 지금처럼 `heading_path`만 사용.
3. 이 폴백은 **목록이 자기 청크의 맨 앞부분(예: start_char가 매우 작은 경우)에서
   시작할 때만** 적용하십시오 — 이미 자기 청크 안에 선행 문장이 있는 목록에는
   손대지 않습니다(기존 정상 동작 보존).
4. 가져온 문장이 실제로 이 목록과 이어지는 문장인지 최소한의 확인이 필요하면,
   문장이 "단," "다만," "아래와 같은 경우" 같은 예외/조건 도입 표현으로 끝나는지
   정도의 가벼운 휴리스틱은 허용되지만, 필수는 아닙니다 — 없으면 그냥 마지막 줄을
   가져오는 것으로 충분합니다(과설계 금지).

## 5. 검증 계획

1. 위 재현 사례(운영정책 2023-04-06, 사적분쟁 예외목록)로 수정 전/후 `context_text`
   비교 — 수정 후 "[3-3] 회사는... 원칙으로 합니다..." 문장이 붙는지 확인.
2. 같은 3개 패러프레이즈로 실제 BGE 점수 재측정 — 격차가 0.05 이내로 줄거나
   역전되는지 확인 (mock 아니고 실제 모델로).
3. 158개 "고아" unit 전체를 재스캔해서, 이번 수정으로 몇 개가 실제로 context를
   회복하는지, 몇 개는 여전히(직전 청크에도 선행 문장이 없어서) 빈약한 채로
   남는지 집계.
4. 이 사례를 실제 재현 텍스트 그대로 단위 테스트에 추가 — 기존 "길드장 권한 위임"
   테스트처럼 인위적인 mock 점수가 아니라, 이번엔 청크 경계 상황 자체를 구성해서
   context 폴백이 발동하는지 확인하는 테스트로.
5. existing32 / new_claim32 adaptive 결과 회귀 없는지 재확인
   (26/32→29/32, 27/32 각각 유지).

## 6. 하지 말 것

- 청킹 파라미터(overlap_chars, 청크 경계 스냅 규칙) 자체를 바꾸지 않습니다 — 이건
  전체 코퍼스 재생성이 필요한 훨씬 큰 변경이고, 이번 수정은 evidence 파생 단계에서
  국소적으로 보강하는 것으로 충분합니다.
- 0.05 마진 값 자체를 조정하지 않습니다 — 그건 별개의 메커니즘이고, 이번 수정으로
  대부분의 경우 격차가 애초에 크게 좁혀지거나 역전되므로 마진 값을 만질 필요가
  없어집니다.
- 두 청크 이상 거슬러 올라가는 fallback을 넣지 않습니다.
- 158개 "고아" unit 전체를 한 번에 수작업으로 검토해서 케이스별 규칙을 넣지
  않습니다 — 이 fallback 하나로 얼마나 회복되는지 먼저 측정하고, 그래도 남는 게
  있으면 그건 별도 사례로 다룹니다.
