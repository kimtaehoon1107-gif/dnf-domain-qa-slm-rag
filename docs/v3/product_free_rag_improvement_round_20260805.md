## 0. v1 지시서의 오류 정정 (Claude)

Codex가 지적한 5건을 전부 원문·코드로 확인했고 **5건 모두 맞습니다.**
같은 오판이 반복되지 않도록 기록합니다.

### 0-1. USER10 slot 2 판정 오류 🔴 (가장 중요)

v1은 제거된 수량을 "나벨 레이드 실제 보상"으로 보고 복구하라고 했습니다.
**틀렸습니다.**

```json
// table_atomic_facts_v3.2_1f29fca9….jsonl line 1636
attribute    : "추가 보상"
heading_path : ["# 아라드 로얄 패스 캐릭터 지정 시 콘텐츠 추가 보상 안내", "* 레이드 던전"]
title        : "아라드 패스 2026 시즌3"
row_text     : "| | 종말의 계시 8개 / 10개 / 16개 / 16개 | 만들어진 신 나벨 - 싱글 / 매칭 / 노말 / 하드 |"
valid_from   : 2026-06-04   valid_to : 2026-08-13
```

`깨진 악몽의 잔해` 12건 전수 확인 결과, **수량이 붙은 것은 전부 이 아라드 패스
문서**입니다. 조건과 유효기간이 붙은 값입니다.

따라서 모델 claim —
> "만들어진 신 나벨 레이드에서 얻을 수 있는 보상은 종말의 계시 8개/10개/16개/16개입니다"

— 는 **아라드 패스 조건을 떨어뜨린 overclaim**이고, **Product가 제거한 것이
정답**입니다. v1 기준대로 복구하면 오답을 만드는 지시가 됩니다.

> **오류의 종류**: claim 텍스트만 보고 "더 구체적이니 더 좋다"고 판단했고
> 근거의 `heading_path`(조건 범위)를 확인하지 않았습니다.
> **교훈: 값의 구체성이 아니라 값이 성립하는 조건 범위를 먼저 확인할 것.**

### 0-2. 세 가드를 한 덩어리로 묶은 것

코드상 **서로 다른 함수, 다른 목적**입니다.

```
product_free_rag.py:932        _cross_parent_clarification()
  → 여러 claim이 서로 다른 parent를 가리킬 때 되묻기를 만드는 후처리

product_minimal_verifier.py:583  _cross_parent_structured_values_supported()
  → 하나의 claim이 여러 parent의 값을 섞는지 검사하는 검증
```

이번 라운드는 **앞의 것 하나만** 손댑니다.

### 0-3. CUDA hook은 Ollama 상태를 기록하지 않음

`record_cuda_memory_diagnostic()`([product_free_rag.py:1492](src/v3/product_free_rag.py:1492))
전문 확인 결과 **Torch 메모리만** 담습니다. `ollama` 필드가 없습니다.
기존 트레이스의 `ollama.size_vram`은 8/3 진단 러너가 별도로 붙인 값이었습니다.

### 0-4. `retrieval_ms` 분해 공식 오류

`v1`의 `model_reload_ms + search_ms ≈ retrieval_ms`는 성립하지 않습니다.
[product_free_rag.py:1882](src/v3/product_free_rag.py:1882)~[1923](src/v3/product_free_rag.py:1923)
사이에 다음이 전부 들어갑니다.

```
질문 정규화 → 메타데이터 라우팅 → Kiwi 절 분해 → 초기화 → 모델 재적재
  → BM25 → dense → 후보 리랭커 → atomic evidence 리랭커 → parent 선택
```

### 0-5. W7 조건 A가 실험이 아니었음

`answer()`에서 **검색이 생성보다 먼저** 실행됩니다. Ollama 재시작 직후 첫
질문이면 Qwen이 아직 VRAM에 없어 **경합이 일어날 수 없습니다.**
"cold 프로세스"와 "Qwen이 VRAM에 상주"를 혼동한 설계였습니다.

실제 288초는 **6번째 질문**에서 났고, 그때는 앞 5회 생성으로 Qwen이 상주
중이었습니다.

### 하지 말 것

1. **도메인 하드코딩 금지** — 문서명·아이템명·직업명·보스명·relation 이름
   허용목록을 만들지 마십시오.

   임계값이 존재하지 않습니다.
3. **광범위한 관계 검증기 구현 금지** — relation ontology, 개체 유형 사전,
   의미 분류 모델, 2차 LLM verifier는 전부 이번 라운드 범위 밖입니다.

4. **소수 케이스 프로브로 판단 금지** — 모든 수정은 저장된 **전체** 출력에
   대해 검증하십시오. (Kiwi 4/4 → 실제 정밀도 10.7% / BGE 7/7 → 임계값 부재)
5. **A6 Qwen 재호출 금지** — 저장 출력 replay만.
6. **채점기 완화 금지** — A6 slot 1처럼 다른 결제수단 값을 쓴 진짜 오답이
   통과합니다.
7. **한 라운드에 여러 가드를 동시에 건드리지 말 것** — v1의 가장 큰 실수입니다.

## W0. 측정 인프라 — **선행 조건, 가장 먼저**

확인된 사실: `reports/v3/product_free_rag_*.jsonl` **63개 파일 전부**에서
`result.candidates[]`에 `text` 키가 없고 `evidence_units`도 없습니다.
저장 출력으로 claim↔evidence를 대조하는 replay가 **구조적으로 불가능**합니다.

### W0-1. 실행 스냅샷 저장 🔴

```
result.evidence_pack = [
  {"ref": "E1", "chunk_id": …, "parent_document_id": …,
   "heading_path": […], "valid_from": …, "valid_to": …,
   "start_offset": …, "end_offset": …, "text": …,
   "unit_kind": "atomic_fact" | "table_row" | …}
]
result.raw_model_output   : verifier 통과 전 Qwen 원문
result.runtime_fingerprint: {corpus_sha, chunk_sha, code_rev, profile}
```

`heading_path`와 `valid_from/valid_to`를 반드시 포함하십시오 — 0-1 오판을
사람이 재현·검증할 수 있어야 합니다.

**통과 기준**: 새 실행 1건에서 `claims[].evidence_refs`와
`rejected_claims[].evidence_refs`가 `evidence_pack`의 ref로 **100% 해소**될 것.

### W0-2. 단계별 지연 계측 🔴

`retrieval_ms` 하나로 뭉쳐 있는 것을 8단계로 분해하십시오.

```
initialization_ms          런타임 초기화
model_reload_ms            CPU → GPU 재적재       ← 지금 숨어 있는 값
question_normalize_ms      정규화 + 메타데이터 라우팅 + Kiwi 절 분해
query_embedding_ms         질의 임베딩
lexical_dense_search_ms    BM25 + dense 검색
candidate_rerank_ms        후보 리랭커
evidence_atomic_rerank_ms  evidence pack atomic 리랭커
model_handoff_ms           GPU → CPU 해제         (기존)
generation_ms              Qwen 생성              (기존)
total_ms
```

**통과 기준**: 3문항 실행에서 위 항목 합계와 `total_ms`의 차이가 5% 이내이고,
각 항목이 개별 기록될 것.
(v1의 `model_reload_ms + search_ms ≈ retrieval_ms`는 **폐기**)

### W0-3. VRAM 상태 기록 🔴

`record_cuda_memory_diagnostic()`은 **Torch 메모리만** 기록합니다
([product_free_rag.py:1492](src/v3/product_free_rag.py:1492)).
두 가지를 모두 해야 합니다.

```
(a) 기존 hook을 모든 평가 러너에 연결 (diagnostics_hook 전달, 기본 활성)
(b) Ollama /api/ps 조회를 hook 스냅샷에 추가
    → models[].name, size, size_vram, expires_at
```

**통과 기준**: 새 실행 결과의 각 stage에 `torch_reserved_bytes`,
`device_free_bytes`, `retrieval_models_offloaded`, **`ollama.size_vram`**이
모두 기록될 것.

## W7. VRAM 경합 A/B — 독립, W0-3 직후 실행

### 확정된 예산

```
그래픽카드 총 VRAM         :  7.96 GiB
Ollama qwen3-8b size_vram  :  5.20 GiB
BGE-M3 + 리랭커 (torch)     :  4.34 GiB (최대 4.38)
                              ─────────
                               9.54 GiB   ← 1.58 GiB 초과, 공존 불가
```

증거: **완전히 같은 질문**이 A6에서 53.0초, AB10에서 3.5초
(후보 8건·근거 8개로 작업량 동일).

### 실험 조건 (v1에서 수정됨)

**속도가 아니라 "검색 직전의 실제 VRAM 상태"가 실험 조건입니다.**

```
[조건 A — resident]
  1. Qwen을 명시적으로 preload
  2. /api/ps에서 size_vram > 0 확인          ← 확인 전에는 진행 금지
  3. Product 검색 실행 (같은 질문)

[조건 B — unloaded]
  1. Qwen을 명시적으로 unload (또는 OLLAMA_KEEP_ALIVE=0)
  2. /api/ps에서 size_vram = 0 확인          ← 확인 전에는 진행 금지
  3. Product 검색 실행 (같은 질문)

질문: "세라 결제취소와 환불은 뭐가 달라?"     (USER10 최초 측정 288.4초)
```

### 판정 기준 (사전 등록)

| 결과 | 해석 | 다음 |
|---|---|---|
| A ≫ B (A 100초↑, B 30초↓) | ✅ VRAM 경합 확정 | 운영 설정 결정으로 |
| A ≈ B (둘 다 빠름) | ⚠️ 다른 원인 | W0-2 단계별 계측으로 재조사 |
| A ≈ B (둘 다 느림) | ❌ 경합 아님 | W0-3 트레이스 전면 재검토 |
| `/api/ps` 확인 누락 | ❌ **실험 무효** | 조건부터 다시 |

### 참고: 해결 후보 (실험 후 결정)

```
① OLLAMA_KEEP_ALIVE=0        → Qwen 재적재 비용을 매번 지불, tail 제거
② 검색 모델을 CPU로           → 스왑 자체 제거. legacy가 14~30초로 tail 없음
③ handoff 비활성 + 작은 양자화 → 4.34 + 4.7 = 9.04, 여전히 초과. 무효
```

> 제품 관점에서 "보통 8초, 가끔 300초"보다 "항상 20초"가 낫습니다.
> 사용자는 평균이 아니라 최악을 기억합니다.

## W2a. 채점기 overclaim 게이트 — **런타임과 분리**

### 문제: 게이트가 구조적으로 죽어 있음

```python
# src/v3/score_product_free_rag_a6.py:250
"unsupported_overclaim_candidate": bool(
    frozen["expected_response_mode"] == "abstain"
    and actual_mode in {"answer", "partial"}
)
```

A6 기대모드는 `{full_answer: 28, partial_answer: 4}`로 **`abstain`이 0건**.
조건 앞부분이 절대 참이 될 수 없어 **항상 통과**합니다.

### 요구사항

```
요구(requirement) 단위로 판정:
  expected_status == "unsupported" 인 요구에 대해
  노출된 답변에 그 요구의 값이 등장하면 → unsupported_overclaim
응답 모드(abstain/partial/answer)와 무관하게 작동
```

**이것은 채점기 변경일 뿐이며 런타임 verifier를 건드리지 않습니다.**
같은 커밋에 섞지 마십시오.

### 회귀 케이스

| 케이스 | 기대 |
|---|---|
| A6 slot 22 (`12/4(목)` 노출) | **overclaim으로 계수** |

| A6 slot 29 (가격만 답하고 제한 미노출) | **계수 안 됨** — 정상 partial |

## W1. `ambiguous_cross_parent_context` 만 수정 — 범위 축소

### 대상 (이것 하나만)

```
[USER10 slot 4] Q: 간편잠금 비밀번호는 어디서 어떻게 바꿔?
  → mode=clarification, 불필요한 C1/C2/C3

  거절: 서비스센터 > 보안 > 간편잠금 > [비밀번호 변경] 버튼   << ambiguous_cross_parent_context
  거절: 홈페이지 서비스센터 [비밀번호 변경] 버튼              << ambiguous_cross_parent_context
  거절: [던파ON - 간편잠금]에서 변경                         << ambiguous_cross_parent_context
  거절: 홈페이지에서 변경                                   << ambiguous_cross_parent_context
  거절: 휴대폰 인증 이후 비밀번호(숫자 6자리) 입력            << ambiguous_cross_parent_context
```

5개가 **서로 모순되지 않습니다.** 1번이 가장 상세하고 2·4번은 부분집합,
3번은 앱 경로, 5번은 다음 단계입니다. 던파 FAQ는 같은 주제를 여러 문서에서
반복 서술하는 것이 정상입니다.

### 건드리지 말 것

| reason | 위치 | 이번 라운드 |
|---|---|---|
| `ambiguous_cross_parent_context` | product_free_rag.py:932 | ✏️ **수정** |
| `weaker_cross_parent_context` | product_free_rag.py:932 | 🔒 **유지** |
| `cross_parent_structured_value_conflict` | product_minimal_verifier.py:583 | 🔒 **유지** |

`weaker`를 유지하는 이유: **USER10 slot 2의 아라드 패스 조건부 값 제거가
이 경로입니다.** 건드리면 0-1의 오답이 부활합니다.

### 요구사항

`_cross_parent_clarification()`의 발동 조건을 **"parent 상이"에서
"값 모순 또는 조건 상이"로** 좁히십시오.

```
되묻지 않을 조건 (전부 만족할 때):
  1. claim들의 정규화된 값이 서로 모순되지 않음
     (숫자·날짜·시각·불리언은 value_normalization 사용)
  2. 한쪽이 다른 쪽의 부분집합 / 상세화임
     (값이 없는 절차·경로는 문자열 포함관계로 판정)
  3. 근거들의 heading_path·valid_from/valid_to가 서로 다른 조건 범위를
     가리키지 않음                                    ← 0-1 재발 방지

→ 위를 만족하면 가장 상세한 claim을 채택하고 되묻지 않는다
→ 하나라도 어기면 기존대로 clarification
```

3번 조건이 핵심입니다. 이게 없으면 아라드 패스 같은 조건부 문서가 "부분집합"
으로 오인될 수 있습니다.

### 회귀 케이스 (되묻는 쪽도 반드시 포함)

| # | 케이스 | 기대 |
|---|---|---|
| 1 | USER10 slot 4 간편잠금 5 claim | **되묻지 않음** — 가장 상세한 경로 채택 |
| 2 | USER10 slot 2 아라드 패스 수량 | **계속 제거** — 조건 범위가 다름 |
| 3 | 서로 다른 parent가 **다른 숫자**를 말하는 합성 케이스 | **계속 되묻기** |
| 4 | 서로 다른 revision의 정책 값 | **계속 차단** |
| 5 | **진짜 모호한 질문** (별도 합성) | **되묻기 유지** ⚠️ |

**5번을 반드시 만드십시오.** slot 4를 고치다가 "되물어야 할 때 안 되묻는"
반대편 실패로 넘어갈 수 있습니다. slot 4(불필요한 되묻기)와 slot 5(되물었어야
하는데 안 되물음)는 정반대 실패이며, 같은 메커니즘을 공유합니다.

### 통과 기준

```
- 회귀 5건 전부 기대대로
- 저장 출력 전건 스캔에서 ambiguous_cross_parent_context 발동 건수 감소
- 새로 통과한 claim 중 값이 모순되거나 조건 범위가 다른 것 0건
- weaker / structured conflict 발동 건수 불변
- 기존 회귀 스위트 전건 green
```

## W2b. 추천·권장 질문 가드 — 범위 축소

### 대상

```
[USER10 slot 8] Q: 나벨 하드 클리어에 추천하는 직업 알려줘
  A: "추천되는 직업은 '엘디르'와 '아니마'입니다."   ← 승인됨. 거절 안 됨

  후보:  ref=1 0.0573  만들어진 신 나벨   ← 채택. 엘디르·아니마는 보스/지역 이름
        ref=4 0.0281  연금술사           ← 진짜 직업 문서인데 점수 낮음
        ref=8 0.0032  인형사
```

**왜 안 걸렸나**: 인용 좌표는 정확하고(E1에 문자열 존재),
`factual_values_supported`는 **숫자·날짜만** 검사하며, 고유명사의 의미 역할을
보는 장치가 없습니다.

### 요구사항 (일반 관계 검증기가 아님)

```
질문이 추천·권장 같은 규범적 답을 요구하면,
근거에도 명시적인 추천·권장 관계 서술이 있어야 한다.
없으면 unsupported.
```

- 직업명·보스명 목록 없이 slot 8을 막을 수 있습니다.
- 규범 질문 판정은 **질문 표면의 어휘 패턴**으로 합니다 (추천/권장/좋아/나아/
  best 등). 도메인 개체가 아니라 질문 유형이므로 하드코딩이 아닙니다.

### ⚠️ 이 가드가 덮지 못하는 것 — 문서에 명시할 것

```
[A6 slot 22] Q: 제보 뒤 답변까지 걸리는 기한은 정확히 며칠이야?  (문서에 없음)
             A: "12/4(목)까지이다"   ← 무관한 공지에서 날짜를 끌어옴
```

**추천 질문이 아니므로 이 가드로는 안 막힙니다.**
W2a(채점기)로 **측정**은 되지만 **런타임에서는 계속 노출됩니다.**

→ **미해결 항목으로 명시적으로 남기십시오.** slot 8만 막고 "overclaim 해결"
로 기록하지 마십시오. 대상·관계 오연결의 일반 해법은 W6 진단 결과를 본 뒤
별도 라운드에서 다룹니다.

### 회귀 케이스

| 케이스 | 기대 |
|---|---|
| USER10 slot 8 추천 직업 | **차단** → unsupported |
| USER10 slot 7 드롭 확률 | **계속 통과** — 정상 보류 |
| USER10 slot 2 나벨 보상 (규범 아님) | **계속 통과** — 동작 불변 |
| 근거에 실제 "추천합니다" 서술이 있는 합성 케이스 | **통과** |

### 통과 기준

```
- 회귀 4건 전부 기대대로
- 저장 출력 전건 스캔에서 새로 차단된 claim 중 실제 정답이었던 것 0건
  (1건이라도 있으면 사례를 보고하고 규칙을 더 좁힐 것)
```

## 부록 — 구조에 대한 메모 (작업 지시 아님)

Codex가 지적한 대로, 현재 한 파이프라인에 성격이 다른 다섯 문제가 들어와
있습니다.

```
1. 공식 문서 사실 검색          ← RAG가 풀 문제
2. 현재·최신 집합 계산           ← RAG가 풀 문제
3. 추천 같은 주관적 질문         ← 라우팅에서 거절할 문제
4. 오늘 날짜·날씨               ← utility 라우팅으로 뺄 문제
5. 이전 대화를 이어받는 멀티턴    ← 세션 레이어 문제
```

**3·4·5는 verifier를 아무리 정교하게 만들어도 풀리지 않습니다.**
검색 전에 걸러야 하는 것들입니다.

그리고 "최소 verifier"를 지향하면서 고유명사 개체 유형 판별, 질문-근거 관계
판별, 문서 간 충돌 판별, 지원/비지원 분리, false-full 0을 동시에 요구하면
결국 Typed verifier로 돌아갑니다. 실제로 cross-parent, surface coverage,
relation role, absence, replacement evidence 가드가 이미 누적됐습니다.

**이번 라운드는 가드를 늘리는 방향이 아니라, 이미 있는 가드 하나를 정확하게
만들고 하나를 좁게 추가하는 것으로 제한합니다.** 구조 재설계는 W6 진단 결과를
본 뒤 별도로 논의합니다.
