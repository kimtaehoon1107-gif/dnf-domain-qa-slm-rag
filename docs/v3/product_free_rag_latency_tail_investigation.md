## 1. 문제 — tail이 재현되지 않습니다

같은 10문항(USER10 v2)의 실행 이력입니다.

| 실행 | p50 | p95 | max | 30초 게이트 |
|---|---:|---:|---:|:---:|
| user10 최초 | 77.5 | 235.1 | **288.4** | ❌ |
| v2 after_improvements (hook ON) | 22.6 | 28.9 | 32.5 | ❌ |
| v2 header_filter | 10.5 | 23.3 | 28.8 | ✅ |
| **v2 hook_off_baseline** | **7.3** | **13.9** | **18.9** | ✅ |
| **v2 hook_off_baseline_retry** | **11.3** | **84.8** | **101.2** | ❌ |
| v2 runtime_r2 (최신) | 7.9 | 21.3 | 28.5 | ✅ |

### 🔴 결정적 관찰

```
hook_off_baseline        max  18.9초
hook_off_baseline_retry  max 101.2초
```

**완전히 같은 설정, 같은 질문, 연달아 실행. max가 5.4배 차이납니다.**

그리고 **6회 중 3회는 30초 게이트를 통과합니다.**

→ **파이프라인이 느린 게 아닙니다. 간헐적으로 멈춥니다.**
→ 질문 탓도, 설정 탓도 아닙니다. 같은 조건에서 났다 안 났다 합니다.

### ⚠️ 게이트 지표 자체의 문제

`n=10`에서 `p95`는 **위에서 1~2번째 값**입니다. A6의 `n=32`에서도 2번째입니다.

**이상치 1건이 게이트 전체를 결정합니다.** 지금 `p95 미달`은
"파이프라인이 느리다"가 아니라 "이번 실행에 이상치가 1건 있었다"는 뜻입니다.

## 2. L1 — 재현성 측정 🔴 **가장 먼저**

### 설계

```
USER10 v2 10문항 × 5회 반복
  · 완전 동일 조건 (현행 런타임, diagnostics_hook OFF)
  · 매 회차 사이에 프로세스를 재시작하지 말 것 (연속 실행)
  · 회차 사이 대기 없음
  · 총 50회 생성
```

### 기록

```
회차별      p50 / p95 / max / 30초 초과 건수
문항별      5회 각각의 wall_ms  (같은 질문이 회차마다 얼마나 흔들리는가)
전체        50건의 지연 분포, 30초 초과 건수와 그 시각
단계별      W0-2 8단계 전부 (initialization / model_reload / question_normalize /
            query_embedding / lexical_dense_search / candidate_rerank /
            evidence_atomic_rerank / model_handoff / generation)
```

### L1 판정 (사전 등록)

| 결과 | 해석 | 다음 |
|---|---|---|
| 30초 초과 **0건** | 이상치가 재현되지 않음 | **L4로 직행.** 게이트 지표 재검토 |
| 30초 초과 있고 **특정 문항에 몰림** | 질문 의존 | L2 — 해당 문항 단계 분석 |
| 30초 초과 있고 **문항과 무관하게 산발** | 환경 의존 | L2 → L3 |

**L1에서 이상치가 안 나오면 L2·L3를 하지 마십시오.** 재현 안 되는 걸
쫓는 게 지금까지 세 번의 실패 원인입니다.

## 3. L2 — 이상치의 단계 특정 (L1에서 재현 시에만)

W0-2 계측이 이미 있으므로 추측 없이 특정됩니다.

```
30초 초과한 각 건에 대해
  · 8단계 중 어디가 부풀었는가
  · 단계 합계와 total의 차이 (미계측 구간)
  · 정상 건의 같은 단계와 비교한 배율
```

**A6 one-shot에서 slot 7은 미계측 구간이 118.9초였습니다.** 그런 경우가
또 나오면 그 구간을 쪼개는 계측을 추가하십시오.

### L2 판정

```
특정 단계가 부풀면       → 그 단계만 파고들 것
미계측 구간이 크면       → 계측을 세분화하고 L1 재실행
모든 단계가 고르게 늘면  → 프로세스 외부 요인. L3
```

## 4. L3 — 이상치 시점의 시스템 상태 (L2에서 필요 시)

```
이상치 발생 건에 대해 기록
  · Torch VRAM (device_free / torch_reserved)      ← W0-3 hook 사용
  · Ollama /api/ps size_vram
  · 프로세스 RSS
  · 이상치 직전·직후 회차와의 차이
```

**측정 hook 자체가 지연을 만들므로**(p50 22.56 vs 11.31 사례),
L3는 **이상치가 재현되는 조건에서만** 켜십시오. 상시 켜지 마십시오.

### 후보 (검증 대상이지 결론 아님)

```
· OneDrive 동기화 — 프로젝트가 OneDrive 폴더 안에 있음
· Windows Defender 실시간 검사
· GPU 드라이버 메모리 압박
· 디스크 I/O 경합
```

**어느 것도 미리 가정하지 마십시오.** L3는 상태를 기록만 하고,
상관이 보이면 그때 개별 검증합니다.

## 5. L4 — 게이트 지표 재검토 🔴 **L1 결과와 무관하게 수행**

```
현행    단일 실행 n=10 또는 n=32 의 p95 ≤ 30초
문제    n=10에서 p95 = 상위 1~2번째 값
        이상치 1건이 게이트를 결정
        같은 조건 6회 실행 중 3회 통과 / 3회 실패
```

### 검토할 것

```
· 단일 실행 p95를 게이트로 쓰는 것이 타당한가
· 대안: N회 반복의 중앙값 p95 / 30초 초과 발생률 / p50 + 최대 허용 이상치 건수
· 제품 관점에서 실제로 중요한 것은 무엇인가
    "사용자가 30초 넘게 기다릴 확률"이 지표라면 발생률이 맞음
```

**지표를 느슨하게 만들려는 게 아닙니다.** 지금 지표는 **재현되지 않는 값을
GO/NO-GO 기준으로 쓰고 있습니다.** 그게 문제입니다.

L4 결과는 **제안만** 하고, 실제 게이트 변경은 사용자 승인 후에 하십시오.

## 6. 하지 말 것

1. **원인 가설을 먼저 세우고 그걸 확인하는 식으로 진행하지 마십시오.**
   L1 분포를 본 뒤에 가설을 세웁니다.
2. **L1에서 이상치가 재현되지 않으면 L2·L3를 하지 마십시오.**
3. **런타임 코드를 고치지 마십시오.** 이 라운드는 측정입니다.
4. **`diagnostics_hook`을 L1에서 켜지 마십시오.** hook이 지연을 바꿉니다.
5. **게이트 기준을 임의로 바꾸지 마십시오.** L4는 제안까지만.
6. **A6 32문항을 돌리지 마십시오.** USER10 v2 10문항으로 충분합니다.
7. **다른 개선(랭킹 결합·예약 fallback)을 이 라운드에 섞지 마십시오.**
   현행 런타임 그대로 측정합니다.
