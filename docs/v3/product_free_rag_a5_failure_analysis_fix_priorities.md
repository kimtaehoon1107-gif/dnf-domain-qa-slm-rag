## 1. 원인을 Codex의 3분류보다 더 세분화했습니다

기존 분류(검색·라우팅 / gold parent 있는데 누락·오결합 / 근거 없는 full)를
실제 `result.claims`/`rejected_claims`를 직접 대조해 아래처럼 재분해했습니다.
**같은 "verifier overreject" 버킷 안에 서로 다른 원인 3개가 섞여 있었습니다.**

### A. 리스트형(value_type=list) factual-value 추출 실패 — slot 3, 7, 8

세 건 모두 **모델이 공식 원문을 토씨 하나 안 틀리고 그대로 claim으로 만들었는데**
`required_factual_value_missing`으로 거절됐습니다.

```
slot 3 거절: "칭호에 부여된 마법부여와 오라에 장착된 엠블렘은 변환 시 삭제됩니다."
  요구값: ["칭호에 부여된 마법부여", "오라에 장착된 엠블렘"]
  → 원문과 완전 일치(공식 문서 그대로)

slot 7 거절: "별·성단·은하 조율자의 저울은 확정 보상으로 각각 유니크 서약 결정,
  레전더리 서약 결정, 에픽 서약 결정을 확정으로 준다."
  → 세 값 모두 각 저울의 공식 원문 <확정 보상> 항목과 일치

slot 8 거절: "변환 뒤 강화/증폭/마법부여 옵션이 유지됩니다."
  요구값: ["강화", "증폭", "마법부여"]
  → 원문 "강화/증폭/마법부여 옵션이 유지됩니다."와 완전 일치
```

같은 문항에서 숫자/날짜형 요구사항(slot3의 `use_limit=1`, slot8의 `price=100000`)은
전부 통과했습니다. **오직 `value_type: list`(여러 개체명 나열)일 때만
factual-value 추출이 실패**합니다. 조사가 붙은 형태("마법부여**와**",
"결정**을**")에서 개체명 경계를 못 잡는 것으로 추정되며, 이건 이 프로젝트가
여러 번 겪은 한국어 조사 처리 불안정성과 같은 계열입니다.

**12건의 실제 제품 실패 중 3건(25%)이 이 한 가지 원인입니다.** 우선순위를
높여야 합니다.

### B. 부정 표현의 동의어 미인식 — slot 22

```
모델: "복구가 불가능하다"
원문: "복구가 가능하지 않습니다"
```
의미는 완전히 같은데 표현이 달라 `factual_values_not_in_evidence`로 거절.
**A와 다른 버그**입니다 — A는 리스트 항목 경계를 못 잡는 것, B는 부정 표현의
동의어(불가능 = 가능하지 않음)를 정규화하지 못하는 것입니다. 같이 고치면 안
됩니다.

### C. cross-parent 충돌 오탐 — slot 15

```
거절: "마법부여 카드와 보주는 1회 거래 시 거래 타입이 계정귀속으로 변경됩니다."
  (원문 그대로)
사유: cross_parent_structured_value_conflict
```
이전 라운드(slot 14, 세라 충전한도)에서는 같은 가드가 **모호성 오판**이었는데,
이번엔 **충돌 오판**입니다. relation 이름만으로 "충돌"을 판정하는 매칭이 너무
느슨해서, 실제로는 무관한 다른 parent의 값과 비교해 충돌로 잘못 보는 것으로
추정됩니다.

### D. relation 라벨 혼동 + 환각 (generation 품질, 코드 버그 아님) — slot 16

```
"등급" 질문 → "+9 증폭 이하 상태"(실은 amplification_requirement 값) 답변
"현재 증폭 수치 조건" 질문 → 완전히 다른 기능(증폭 보호권) 설명 환각
```
검증기 문제가 아니라 Qwen이 relation을 헷갈린 경우입니다. 코드로 결정론적으로
고치기 어렵고 프롬프트 개선 대상입니다. **이번 라운드 수정 범위에서 제외**하고
별도 트랙으로 남깁니다.

### E. 두 번째 요구사항 완전 누락, 거절 기록 없음 — slot 27, 28

```
slot27: sale_period(판매기간) claim/rejected_claim 둘 다 없음. deletion_at만 답변.
slot28: contents(상자 내용물) claim/rejected_claim 둘 다 없음. deletion_at만 답변.
```
verifier가 거절한 흔적이 없다는 게 중요합니다 — **Qwen이 애초에 이 요구사항에
대한 claim을 시도조차 안 한 것**으로 보입니다. 근거가 evidence pack(E1~E8)에
없어서 못 봤는지, 봤는데 안 썼는지 구분이 안 된 상태입니다. **코드 수정 전에
반드시 원인부터 분리**해야 합니다(4번 참고).

### G. metadata 라우팅 오류 — slot 31 (1단계, 재확인 결과 이미 수정된 것으로 보임)

```
질문: "...칭호 전체 표 두 개를 보여줘"
실제: "전체"라는 단어에 걸려 "지금 열려있는 이벤트 개수" metadata 질의로 라우팅,
```

### H. slot 31 2단계 — RAG/표 경로 진입 후의 별도 버그 (신규 발견, 2026-08-04)

라우팅이 올바르게 RAG/표 경로로 온 뒤에도, 그 안에서 세 가지 독립된 문제가
남아 있습니다.

**H1. nominative subject 정규식이 "새해맞이"를 오분석**

```python
_NOMINATIVE_SUBJECT = re.compile(r"^(.{1,36}?)(?:이|가)\s+")
# "새해맞이 이벤트..." 매칭 → group(1) = "새해맞"  (직접 재현 확인)
```
"새해맞이"의 어간 끝 "이"를 조사로 착각합니다. 형태소 분석기를 새로 넣지 않고,
**표 질문에서는 nominative subject 추론 자체를 쓰지 않도록 범위를 좁히는** 것으로
수정합니다.

```
회귀 조건:
- "새해맞이 이벤트 ... 표" → subject []
- "장비가 초월이 안돼" → subject ["장비"] 유지
- "장착 칭호가 해제되지 않을 때" → subject ["장착 칭호"] 유지
```

**H2. 표 제목을 "표 직전 문장"이라는 위치 기반 휴리스틱으로 결정 → 질문-표 셀 대조로 변경**

지금은 표 바로 앞 문장을 제목으로 씁니다(청크 경계 문제 때와 같은 계열의
위치 기반 취약점). 대신 **선택된 질문 focus와 실제 표 셀 값을 대조**해서
제목을 정합니다. 정확히 겹치는 셀이 없으면 기존 직전 heading을 fallback으로
유지합니다. 특정 칭호명·열 이름을 코드에 하드코딩하지 않습니다.

```
질문 focus: 이달의 행운아  ×  표 셀: 이달의 행운아  →  제목: 이달의 행운아
```

**H3. 순수 표 질문에서 Qwen의 불필요한 설명문 제거 — 프롬프트가 아니라 서버 렌더러에서 결정론적으로 처리**

```
조건: 질문에 표 요청이 있음 + 채택한 근거가 모두 complete table
  → Qwen claim 문장은 최종 답변에 노출하지 않고, 서버가 표 제목 + 원문 표만 출력
Qwen은 여전히 T1·T2를 선택하고 verifier도 통과해야 함 (내부 계약은 유지)
서술형 근거와 표 근거가 섞인 질문에서는 기존 claim을 그대로 유지
  (일반 답변이 사라지는 부작용 방지)
```

**H 진행 순서**: H1(표 질문 subject 추론 비활성화) → H2(question-focus 기반 표
제목 결정) → H3(순수 표 응답 Qwen 설명 숨김) → 각각 단위 테스트 → 관련 회귀
전체 실행 → 해당 문항만 adaptive 단일 재현 → **A5 전체는 재실행하지 않음**.

## 3. 검증 계획

- 1~5는 각각 위 검증표의 최소 재현 케이스로 단위 테스트 추가.
- 6은 코드 수정 전에 evidence pack 로그부터 확인 — 원인이 갈리면 그에 맞는
  targeted diagnostic을 따로 설계.
- 전체 수정 후 existing32 / new_claim32 재실행 — 기존 통과 문항 회귀 없는지 확인.
- A5 원본 12건 실패 케이스를 같은 입력으로 targeted replay(단, A5 자체를
  "실행"으로 재선언하지 않고 실패 진단용 replay로만 기록)해서 몇 건이 해소되는지 집계.
- 다음 독립 성능 측정은 이번 수정들이 끝난 뒤 완전히 새로운 세트로 진행.

## 4. 하지 말 것

- A5를 다시 "실행"하지 않는다 (진단용 replay와 공식 one-shot 실행을 명확히 구분).
- A(리스트형 값)와 B(부정 표현)를 같은 수정으로 묶지 않는다 — 원인이 다르다.
- slot 16(relation 라벨 혼동)을 이번 코드 수정 범위에 넣지 않는다 — 결정론적
  수정이 아니라 프롬프트/모델 품질 문제다.
- slot 27/28을 원인 구분 없이 바로 "생성 완전성 문제"로 단정하고 프롬프트만
  고치지 않는다 — evidence pack 확인이 먼저다.
- 이번 수정들을 검증한다고 A5를 재실행하지 않는다.
- H1을 형태소 분석기 신규 도입으로 확장하지 않는다 — 표 질문에서 subject
  추론을 끄는 최소 범위로 한정한다.
- H2에서 특정 칭호명·열 이름("칭호명" 등)을 코드에 하드코딩하지 않는다 —
  질문-표 셀 대조라는 일반 규칙만 사용한다.
- H3을 프롬프트 지시문만으로 재시도하지 않는다 — 서버 렌더러에서 결정론적으로
  처리해야 재발하지 않는다.
