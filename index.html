DNF Domain QA SLM/RAG v2

답하는 것보다,
언제 거부해야 하는지가 더 어려웠습니다.

DNF 문서 기반 LLM 평가(v1)를 baseline으로, 데이터 설계·라벨링부터 RAFT 학습 데이터 구성, LoRA 파인튜닝까지 확장한 개인 프로젝트입니다.

Problem

이 프로젝트 시리즈의 전체 목표는, 좁고 깊은 도메인에서 모델이 근거를 기반으로 답하고 근거가 없으면 스스로 거부할 수 있는 신뢰 가능한 QA 시스템을 재현 가능한 방식으로 만드는 것입니다. v1이 이 문제를 평가 방법론으로 검증했다면, v2는 그 방법론을 실제 데이터 구축과 파인튜닝으로 확장한 단계입니다.

RAG를 붙여도, "모른다"고 말하는 건 따로 보장되지 않습니다

v1에서 검색과 생성을 각각 분리해 측정하고 개선했지만, 그것만으로는 풀리지 않는 문제가 남아있었습니다. 모델이 검색된 근거를 잘 활용해서 답하는 것과, 애초에 근거가 없는 질문에 답을 지어내지 않고 거부하는 것은 서로 다른 능력이라는 점이었습니다.

v2의 목표는 그럴듯한 챗봇을 만드는 것이 아니라, "이 질문에 답할 근거가 있는가"를 모델이 스스로 판단하게 만드는 것이었습니다. 이를 위해 평가만 하던 v1에서 한 걸음 더 나아가, 데이터를 직접 설계하고 모델을 파인튜닝하는 단계까지 수행했습니다.

Approach

근거·거부 판단을 학습시키는 4단계

접근은 "판단 기준을 정의 → 그 기준으로 학습 데이터를 만들고 → 모델에 가르친 뒤 → 한 번도 안 본 데이터로 실제로 배웠는지 확인"하는 순서로 설계했습니다.

01 · 기준 정의

데이터 라벨링 설계

정답·부분정답·거부를 구분하는 스키마와 라벨링 가이드를 직접 설계하고 Label Studio 워크플로우를 구축했습니다.

02 · 학습 데이터

RAFT 학습 데이터 구성

정답 근거뿐 아니라 헷갈릴 만한 distractor 근거와 거부 사례를 함께 넣어, "근거가 없을 때"도 학습하도록 설계했습니다.

03 · 학습

LoRA 파인튜닝

Qwen2.5-0.5B-Instruct를 로컬 GPU로 파인튜닝해, 프롬프트만으로는 안정화되지 않던 거부 판단을 모델에 직접 학습시켰습니다.

04 · 검증

3종 held-out 평가

학습 분포와의 거리가 다른 domain expanded·official·fresh 세 세트로 나누어, 실제로 일반화됐는지 따로 확인했습니다.

Finding

예상은 반은 맞고, 반은 틀렸습니다

파인튜닝하면 거부 판단이 전반적으로 안정될 거라고 예상했습니다. 학습 데이터와 분포가 가까운 domain expanded와 official 세트에서는 이 예상이 맞았습니다.

EvalAnswerability비고
Domain expanded (120건)1.0000학습 데이터와 같은 분포
Official (30건)1.0000공식 문서 기반, 형식은 유사
Fresh (30건)0.4333한 번도 학습에 쓰이지 않은 새 질문
진단 — "보수적 거절 편향"
하지만 한 번도 학습에 쓰이지 않은 fresh 세트에서는 0.4333에 그쳤습니다. 원인을 들여다보니 검색 실패가 아니었습니다. 거부해야 할 질문은 fresh에서도 8/8을 정확히 걸러냈지만, 구어체로 바뀐 정답 가능한 질문까지 과도하게 거부하고 있었습니다. 즉 모델이 "모르면 거부"가 아니라 "낯설면 거부"를 학습한 것이었고, 이는 검색기를 바꿔서 풀리는 문제가 아니라 학습 데이터의 표현 다양성이 부족해서 생긴 문제였습니다.
