# DNF 공식 문서 QA/RAG v3 정직한 천장 캡스톤

상태 기준일: 2026-07-21  
소스 기준 커밋: `734516899e7f12acd52329fc14a7678a002f535d`  
역할: 현재 v3 연구 상태의 단일 출처(single source of truth)  
판정: **컴포넌트 수준 진전은 확인했지만, 전체 runtime은 NO-GO**

## 1. 이 문서의 권한과 범위

이 캡스톤은 기존 프로즌 산출물의 숫자와 판정을 새 실행 없이 통합한 문서다. 기존 handoff의 장기 목표, v3 재현성 기준선, frozen provenance와 blind 보호 계약은 그대로 유효하다. 다만 과거의 Cycle 1~7 진행 순서와 상태 표시는 이 문서의 `8. 재조정된 로드맵`이 대체한다.

이번 통합에서 새 모델 실행, 새 측정, 학습, gold·라벨·질문 수정, canonical/runtime 승격은 하지 않았다. 기존 frozen blind도 열거나 검색하거나 평가하지 않았다.

## 2. 조사된 아키텍처와 실제 여정

v3가 검증한 파이프라인은 다음 순서다.

`hybrid 검색 → semantic planner 요구 열거 → 요구별 후보 선택/reranking → chunk-diverse exact assembler → groundedness 기반 routing·partial·abstain`

핵심 변화는 질문 전체를 한 번에 생성하는 구조에서 벗어나, 요구를 원자적으로 열거하고 이미 검색된 공식 문서의 정확한 원문 구간만 선택·인용하는 구조로 이동한 것이다. 자연어 생성은 이 검증 경로에 포함하지 않았다.

## 4. Answerability의 정직한 경계

현재 증거로 가능한 부분과 불가능한 부분을 분리한다.

- 기계적으로 가능한 고정밀 reject: 검색 후보가 0인 조건에서 reject 8/11, 답 가능한 질문 오거부 0/82.
- 임계 완화의 한계: 후보 수 `<2`는 reject 9/11로 늘지만 답 가능한 질문도 2/82 잘못 거부한다.
- realtime·개인 질문: 정적 문서가 존재하거나 관련 표현을 포함할 수 있어 검색 신뢰도만으로 안전하게 분리되지 않았다. zero-FP 조건에서 realtime 회수는 0/2다.
- 따라서 현재 안전 동작은 문서가 실제로 지지하는 요구만 exact citation으로 답하고, 미지지 요구는 `문서에서 확인 불가`로 표시하는 것이다. 별도 answer-source 분류기는 채택하지 않는다.

이는 개인·실시간 분류가 해결됐다는 뜻이 아니다. **오답을 만들지 않는 abstain 경로를 확보했을 뿐이며, 정확한 realtime API route는 표본도 2건이라 유보 상태다.**

## 5. False-full 9건의 실제 단계 귀속

백본의 runtime NO-GO를 만든 9건을 기존 프로즌 감사가 다음처럼 분해했다.

| 유형 | 건수 | 의미 |
|---|---:|---|
| A. `WRONG_ATTRIBUTE` | 2 | 올바른 문서가 검색됐지만 판매일·삭제일 같은 형제 속성을 잘못 인용. post-retrieval의 진짜 하드코어 |
| B. `RETRIEVAL_MISS` | 6 | 정답 근거가 후보에 없어서 distractor를 full로 처리. 검색 recall 문제 |
| C. `MEASUREMENT_ARTIFACT` | 0 | proxy gold 오판으로 설명되는 사례 없음 |
| D. `CROSS_PARENT_MISS` | 1 | 필요한 근거가 다른 parent에 있는데 full로 처리. 검색/parent coverage 문제 |

즉 9건 중 검색·parent coverage 쪽이 7건(`B6 + D1`), 형제 속성 판별이 2건이다. 측정 artifact는 0이다. 심각도는 citation을 보면 비교적 바로 잡을 수 있는 `catchable` 6건, 인용을 봐도 미묘한 `subtle` 3건이다. 형식은 미지지 요구를 full로 표시한 7건과 틀린 값을 제시한 2건이다.

따라서 현재 정직한 ceiling은 다음과 같다.

- exact slicing 자체는 100%로 고정할 수 있다.
- 하지만 `원문을 그대로 인용했다`는 사실만으로 `그 인용이 요구에 답한다`는 의미 지지는 보장되지 않는다.
- 프로즌 verifier A/B에서는 grounded 73을 유지하면서 이 9건을 유의미하게 줄이는 운영점을 찾지 못했다.

## 6. 결과에서 도출된 설계 원리

v3의 현재 원리는 **“열거와 기계적 실행은 제한된 계약 아래 신뢰하고, 의미 분류와 자유 생성은 검증 없이 신뢰하지 않는다”**다.

- 신뢰 범위: planner의 원자 요구 열거, content-addressed 입력, 기존 후보에서의 deterministic reranking, 원문 offset을 이용한 exact slicing, 요구별 unsupported/partial 표기.
- 불신 범위: answer-source를 한 번에 맞히는 분류, 작은 모델의 span 복사·선택 판단, 단일 global threshold의 semantic support 판정, 인용되지 않은 자유형 답변 생성.
- 아키텍처 결과: planner는 열거 전용, assembler는 mechanical extractive, answerability는 고정밀 reject와 정직한 abstain, runtime 승격은 false-full이 남아 있는 동안 보류한다.

이는 모델이나 의미 판단을 영구히 배제한다는 선언이 아니다. 현재 프로즌 실험에서 안전 gate를 넘은 범위만 신뢰한다는 연구 규율이다.

## 7. 남은 레버 — 명명만 하며 아직 실행하지 않음

1. **7건 요구별 검색**: `RETRIEVAL_MISS 6 + CROSS_PARENT_MISS 1`에 대해 requirement-targeted retrieval과 parent coverage를 별도 실험한다.
2. **2건 형제 속성 판별**: 같은 문서 안의 인접 속성 값을 구분하는 attribute-specific support 판단을 별도 실험한다.
3. **Cross-parent n=2 유보**: 현재 표본으로 route 결론을 확정하지 않는다. 새 독립 표본과 사전 고정 gate 전에는 승격하지 않는다.

이 항목들은 다음 연구 후보이지 이번 캡스톤에서 실행하거나 승인한 작업이 아니다.

## 8. 재조정된 로드맵

| 기존 로드맵 | 실제 상태(정정) |
|---|---|
| 장기 목표 | **유효·불변**. 공식 문서 기반의 최신성·revision 안전 QA/RAG와 정직한 근거 제시라는 목표를 유지 |
| Cycle 1 — Planner answerability FP=0 | planner 열거는 GO. answer-source 분류 경로는 prompt 3회와 분리 A/B에서 NO-GO. 기계적 zero-candidate reject + 미지지 요구의 정직 abstain으로 안전 동작을 대체했으나 runtime 전체는 아직 NO-GO |
| Cycle 2 — Requirement-aware reranker | **완료(통합 경로 기준)**. standalone reranker의 단독 승격은 NO-GO였지만, chunk-diverse exact assembler가 regression 0으로 component GO를 통과하여 요구별 선택·인용 경로를 완성 |
| Cycle 3 — Temporal/Revision verifier | **부분 완료**. 운영정책 temporal router는 개발 GO; broad temporal routing·최종 benchmark는 미완. citation semantic-support verifier는 NO-GO |
| Cycle 4 — 새 sealed canary | **미완**. 기존 frozen blind는 보존·미접근. 이미 열어 진단한 canary는 adaptive validation이며 sealed benchmark로 재사용하지 않음 |
| Cycle 5 — Extractive Generator | **컴포넌트 수준 사실상 완료**. exact citation assembler, 자유생성 0. 다만 false-full 때문에 end-to-end runtime은 NO-GO |
| Cycle 6 — 제품화 | **미완**. 앱 통합, 구조화 store, API route는 진행하지 않음 |
| Cycle 7 — 최종평가·선택 학습 | **미완**. final sealed benchmark와 선택 학습은 시작하지 않음 |

이 표가 기존 handoff의 낡은 Cycle 1~7 상태와 순서를 supersede한다. 기존 handoff의 frozen baseline provenance, 재현성 기준선, blind 보호 계약은 변경하거나 대체하지 않는다.

## 9. 현재 결론과 다음 gate

현재 v3는 planner 열거와 exact assembler라는 재사용 가능한 GO 컴포넌트를 얻었다. 그러나 end-to-end runtime은 false-full 9건과 cross-parent 회수 0/2 때문에 NO-GO다. 특히 9건 중 7건은 post-retrieval verifier가 아니라 검색/parent coverage에서 먼저 깨졌고, 나머지 2건은 같은 문서의 형제 속성 판별 문제다.

그러므로 다음 단계는 전체 시스템 승격이나 새 생성기가 아니다. 위 두 원인군을 서로 분리한 개발 실험을 사전 계약하고, 그 뒤 새 독립 sealed canary에서 한 번 검증해야 한다. 그 전까지 이 캡스톤의 최종 상태는 다음과 같다.

`Planner enumeration GO + Exact assembler GO + Temporal partial + Answer-source classifier NO-GO + Semantic verifier NO-GO + Backbone dev-GO/runtime NO-GO`
