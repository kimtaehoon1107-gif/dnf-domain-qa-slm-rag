# DNF 공식 문서 QA/RAG v3 정직한 천장 캡스톤 — 최종 갱신

상태 기준일: 2026-07-21  
문서 역할: v3 조사 상태의 단일 출처(single source of truth)  
최종 판정: **검증된 컴포넌트는 보존하지만 end-to-end runtime과 canonical 승격은 NO-GO**

## 1. 권한과 범위

이 문서는 기존 캡스톤을 삭제하거나 덮어쓰지 않고, 이후 동결된 federated 검색 A/B, P1 독립 adjudication, P2 corpus hygiene 재측정을 통합한 후속 content-addressed artifact다. 기존 frozen baseline provenance, 장기 목표, blind 보호 계약은 그대로 유지한다. 이번 갱신에서는 새 검색, 모델 실행, 측정, 학습, gold·라벨·질문 변경, runtime/canonical 승격을 하지 않았다.

기존 캡스톤 `b3655a2478626c068aa8138ba65b7829b5fd8560dbf0214a12694828b940971e`의 컴포넌트 판정은 유지된다.

- Semantic requirement planner enumeration: **GO**. 강한 재매칭 기준 downgraded 32-set 약 90%, adaptive dev 약 98%의 directional recall.
- Chunk-diverse exact assembler: **컴포넌트 GO**. combined all-groups 59/73→73/73, human-gold 78/109→93/109, strict regression 0, exact slice 397/397, LLM 호출 0.
- Answer-source classifier: **3회 연속 NO-GO**. 고정 모델에서 docs FN 24 requirements/15 questions, FP 2 requirements/1 question.
- Semantic-support verifier: **NO-GO**. false-full을 줄이면서 grounded 73을 유지하는 threshold가 없었다.
- Groundedness backbone: **development GO / runtime NO-GO**. 기준선은 grounded 73/82, false-full 9/82, reject 11/11, realtime safe-abstain 2/2, cross-parent trigger 0/2.

## 2. 이후 동결 결과

### 2.1 요구별 검색: NO-GO

동결 planner requirement를 검색 질의로 사용한 query arm은 검색-바운드 7건을 하나도 grounded로 회수하지 못했다. 질문 후보와 요구별 후보의 union은 grounded 73→64, false-full 9→18이었고, requirement-only는 grounded 73→63, false-full 9→19였다. 7건 중 6건은 frozen hard route가 gold source를 애초에 제외한 source-envelope 문제였고, 나머지 1건은 route가 맞아도 requirement top-10에서 놓쳤다.

판정: **query-formation 단독 레버는 NO-GO**. 검색 질의만 늘리면 후보 정밀도와 최종 groundedness가 무너졌다.

### 2.2 Federated recall-first 검색: NO-GO

hard source filter를 제거하고 전 공식 source를 검색한 federated quota arm은 검색-바운드 7건 중 5건을 grounded로 회수했다. 그러나 strict 기준 전체 grounded가 73/82→63/82로 감소했고 false-full은 9/82→19/82로 증가했다. global arm도 grounded 63/82였다. temporal/revision/preview 위반은 0, reject 11/11과 realtime safe-abstain 2/2는 유지됐지만 핵심 grounded guard를 통과하지 못했다.

판정: **federated 검색은 NO-GO**. source routing 제거는 recall을 올렸지만 distractor와 잘못된 인용을 더 크게 늘려 순손해였다.

### 2.3 Federated quota 회귀 17건 P1 adjudication

strict regression 17건을 기존 gold를 변경하지 않고 독립 검토 가능한 형태로 분류했다.

| 분류 | 건수 | 의미 |
|---|---:|---|
| `EQUIVALENT_OFFICIAL` | 9 | 다른 공식 근거가 같은 사실을 지지할 가능성이 있어 사람 확인 대기 |
| `NAVIGATION_CONTAMINATION` | 3 | shop navigation 또는 policy revision selector를 인용 |
| `PERSONAL_SUBJECTIVE_LABEL` | 1 | 정적 문서 정답으로 간주하면 안 되는 라벨 경계 |
| `PARTIAL_SUPPORT` | 1 | 요구 전체가 아닌 일부만 지지 |
| `REAL_WRONG` | 3 | 실제 잘못된 근거 |

원 acceptable set 기준 strict 결과는 grounded 63, false-full 19이며 net grounded loss는 10이다. 9개 `EQUIVALENT_OFFICIAL` 후보가 모두 사람에게 확인된다는 가정에서만 provisional grounded 72, false-full 10이 된다. acceptable sibling 적용 건수는 0이며 gold·strict 지표는 변경되지 않았다. 따라서 “17건 전부 실제 참사”라는 해석은 과장이지만, adjudication이 federated arm을 GO로 바꾸지는 않는다.

### 2.4 P2 corpus retrieval hygiene: NO-GO

검색 모델과 downstream 로직을 고정한 채 `retrieval_text`에서 측정된 navigation/footer/policy selector를 제거했다.

- 3,599개 청크 중 560개 수정
- 검색 투영에서 97,081자 제거
- `display_text`, chunk ID, parent ID, citation offset과 gold ID 보존
- 새 evidence span 손실 0, exact span 396/396
- clean corpus SHA-256: `61d858ef5b7df3a3c157e65dba9dd6991f1daa74bbd2067f17b2438e1c01b5b8`

재색인 후 전체 결과는 grounded 73/82→72/82, false-full 9/82→10/82였다. evidence-group candidate recall도 96/109→95/109로 1건 감소했다. 새 회귀는 정답 청크 내용이 바뀐 것이 아니라 전역 점수 분포 변화로 gold가 dirty rank 10에서 clean rank 20으로 밀린 candidate-depth 경계였다. P1 navigation 3건 중 정책 selector 1건만 해결됐고 shop 2건은 계속 false-full이었다.

판정: **P2 hygiene는 NO-GO**. 오염 청소 자체는 필요하지만 현재 파이프라인의 false-full을 해결하는 독립 레버는 아니며, dirty canonical을 대체하지 않는다.

## 3. 최종 천장 판정

동일한 73/82 grounded 기준선에서 서로 다른 네 레버가 모두 gate를 통과하지 못했다.

| 레버 | 겨냥한 병목 | 결과 |
|---|---|---|
| Semantic-support verifier | 인용 span이 요구에 실제 답하는지 판별 | grounded 73을 유지하면서 false-full 감소 불가 — NO-GO |
| Requirement-query retrieval | 7개 검색-바운드 요구 회수 | 0/7 회수, grounded 64 또는 63 — NO-GO |
| Federated retrieval | hard source routing 때문에 제외된 source 회수 | 5/7 회수했지만 grounded 63 — NO-GO |
| Retrieval-text hygiene | nav/footer/revision distractor 제거 | grounded 72, false-full 10 — NO-GO |

이 결과로 현재 v3의 **정직한 개발 천장**을 다음처럼 확정한다.

- 안정적으로 보존 가능한 bounded 동작은 requirement enumeration, deterministic reranking, exact offset slicing, unsupported/partial 표기다.
- strict 기준 약 9/82 false-full은 현재의 소형 모델·평탄화된 corpus·추출 인용 구조에서 제거하지 못한 잔여다.
- 9건을 절대적인 이론 상한으로 해석하지 않는다. 이는 현재 frozen data/task/architecture에서 네 직교 레버가 실패한 **실측 개발 천장**이다.
- P1을 반영하면 일부 strict failure는 annotation coverage 문제일 수 있지만, sibling이 아직 적용되지 않았으므로 canonical 숫자는 계속 73 grounded / 9 false-full이다.
- runtime, canonical, sealed benchmark, productization은 계속 NO-GO다.

## 4. v3.2 future work — corpus 근본원인

다음 항목은 이번 캡스톤에서 실행하거나 승격한 결과가 아니라, 다음 버전에서 별도 계약·gate로 검증할 방향이다.

1. **Offset-preserving clean evidence view**  
   검색용 `retrieval_text`만 정리해서는 assembler가 인용하는 dirty `display_text`를 차단하지 못했다. 원문 offset은 보존하면서 navigation·footer 구간을 선택 불가로 표시하는 segment eligibility mask 또는 clean evidence view가 필요하다.

2. **표의 row-level atomic fact와 속성 귀속**  
   평탄화된 표에서는 상품명·가격·판매기간·삭제일·거래타입이 인접 행이나 형제 속성에 섞인다. parent, table, row, entity, attribute, value와 원문 offset을 함께 보존하는 atomic representation이 필요하다.

3. **전 출처 temporal/revision 계약**  
   `status`, `valid_from/to`, `revision_id`, current revision뿐 아니라 동일 조항·상품·이벤트 family의 시간 계보와 실제 validity evidence를 연결해야 한다. 현재/과거/비교 mode별 exposure를 별도 gate로 측정한다.

4. **Duplicate family 모델링**  
   이벤트 홍보 페이지, 세리아샵 상품 페이지, 이달의 아이템 과거 문서처럼 같은 대상의 서로 다른 공식 parent를 무조건 중복 제거하지 않는다. `same_entity`, `marketing_detail`, `shop_detail`, `revision_of` 관계로 묶고 질문 요구에 맞는 역할을 선택한다.

5. **긴 정책 문서 재청킹**  
   운영정책은 조항·표·시행 revision 경계를 보존해 재청킹하고, 동일 조항의 현재·직전 revision을 직접 연결한다. 전체 revision을 서로 contradiction으로 간주하지 않는다.

6. **승격 gate**  
   dirty canonical과 별개로 새 corpus를 content-addressed freeze한 뒤, gold content 손실 0, exact offset 100%, candidate recall 비회귀, grounded ≥73, 새 false-full 0, temporal leak 0을 모두 통과해야 한다. 한 번에 여러 hygiene 규칙을 합치지 않고 원인별 독립 arm으로 blast radius를 측정한다.

### 설계 대조 축

v3.2 설계에서는 다음 계열을 구현 정답으로 선결정하지 않고 비교 기준으로만 사용한다.

- **TableRAG 계열**: 표를 평문이 아니라 행·열·속성 단위 근거로 다루는 방향과 대조한다.
- **VersionRAG 계열**: 문서 revision과 질의 시점을 검색·검증 계약에 포함하는 방향과 대조한다.
- **Contextual Retrieval 계열**: 청크에 부모·절·시점 문맥을 부여하되, 오염된 본문을 문맥으로 증폭하지 않도록 clean evidence view 이후에 평가한다.
- **Databricks/Azure/Docling 계열**: layout-aware parsing, 표·섹션 provenance, 원문 위치 추적을 위한 기업·오픈소스 ingestion 설계와 대조한다.

이 대조는 문헌·제품 채택 판정이 아니며 이번 캡스톤에서 실행·측정·승격하지 않았다.
